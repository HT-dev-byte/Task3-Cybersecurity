# Cross-Site Request Forgery Security Testing

## Objective and Scope

This section documents the testing and analysis of a **Cross-Site Request Forgery (CSRF)** vulnerability against **Damn Vulnerable Web Application (DVWA)** in a controlled Kali Linux laboratory environment.

The objective was to demonstrate how a vulnerable state-changing function can be triggered using an authenticated user's existing session and to examine the token-based security mechanism used to prevent unauthorized requests.

## 1. Vulnerability Description and Execution

### Vulnerability Discovered

The tested state-changing functionality was found to be susceptible to CSRF when the application relied primarily on the user's existing authenticated session to authorize the request.

A CSRF vulnerability occurs when an application does not sufficiently verify that a state-changing request was intentionally initiated by the authenticated user.

### Execution Process

The legitimate request generated by the application's state-changing functionality was first observed using **Burp Suite**. The request parameters and session information were examined to understand how the application processed the action.

A proof-of-concept request was then constructed to demonstrate whether the same action could be triggered without being intentionally initiated through the application's normal interface.

The request was submitted while an authenticated session was active.

### Result

The application processed the unauthorized request using the authenticated session, demonstrating the potential for a CSRF attack.

The result showed that an attacker could potentially cause a logged-in user to perform an unintended state-changing action if the application does not require an additional mechanism to verify the origin and authenticity of the request.

## 2. Impact

CSRF can allow an attacker to cause an authenticated user to perform actions without their explicit intention.

Depending on the application's functionality, potential consequences may include:

* Modification of account information
* Changes to account settings
* Unauthorized transactions
* Changes to security-related settings
* Other state-changing operations available to the authenticated user

The potential impact depends on the privileges of the affected account and the functionality exposed by the application.

## 3. Mitigation and Prevention

The primary defense against CSRF is the use of **Anti-CSRF Tokens**.

### Token Generation

The server generates a unique, unpredictable token associated with the user's authenticated session.

### Token Placement

The token is included with state-changing requests, commonly as a hidden field within forms.

### Server Verification

When the request reaches the server, the application verifies that the submitted token matches the token associated with the user's session.

Conceptually:

```text
User submits request
        ↓
Server receives request
        ↓
Validate session
        ↓
Validate CSRF token
        ↓
Token valid?
   ┌────┴────┐
  Yes        No
   ↓          ↓
Process     Reject
request     request
```

### Attack Prevention

An attacker constructing a malicious external request does not normally have access to the victim's unique CSRF token. Consequently, the forged request will lack a valid token and should be rejected by the server.

Additional defenses can include appropriate `SameSite` cookie settings, origin/referrer validation where appropriate, and requiring additional confirmation for particularly sensitive operations.

## Conclusion

The CSRF exercise demonstrated the risk of allowing state-changing requests to rely solely on an authenticated session. Without adequate request validation, an attacker may be able to cause a logged-in user to perform unintended actions.

Implementing unpredictable anti-CSRF tokens and validating them on the server provides an effective defense by ensuring that state-changing requests contain information that an external attacker cannot legitimately provide.
