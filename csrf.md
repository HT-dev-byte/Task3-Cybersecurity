# Cross-Site Request Forgery Security Testing

## Objective and Scope

This section documents the testing and analysis of **Cross-Site Request Forgery (CSRF)** protection against **Damn Vulnerable Web Application (DVWA)** in a controlled **Kali Linux** laboratory environment.

The objective was to examine a state-changing password functionality, inspect the associated HTTP request using **Burp Suite**, and determine whether the application implemented an anti-CSRF token.

## 1. Vulnerability Description and Testing

### Vulnerability Investigated

CSRF occurs when an application allows a state-changing request to be performed using an authenticated user's session without sufficiently verifying that the request was intentionally initiated by that user.

The DVWA password-change functionality was selected for testing because changing a password is a state-changing operation.

### Testing Process

The password-change functionality was accessed while authenticated to DVWA. **Burp Suite Proxy** was used to intercept the HTTP request generated by the application.

The captured request was then inspected to identify the parameters and security mechanisms associated with the password-change operation.

The request contained the password-change parameters and the authenticated session information. However, inspection of both the request and response found **no dedicated CSRF token**.

The captured request did contain a `Referer` header pointing to the relevant DVWA page. However, this was treated as normal browser request information rather than an anti-CSRF token.

### Result

The testing demonstrated that the password-change request **did not contain a dedicated anti-CSRF token** at the tested DVWA security level.

The testing did **not** involve successfully changing another user's password or executing a forged request. Therefore, the result is documented as an observation of missing token-based protection rather than a successful end-to-end CSRF exploitation.

**Evidence:** A screenshot of the Burp Suite HTTP request showing the password-change parameters and the absence of a CSRF token is included in the security-testing evidence.

## 2. Impact

The absence of token-based CSRF protection can increase the risk that an attacker could attempt to cause an authenticated user to perform an unintended state-changing action.

Depending on the application's functionality, potential consequences could include:

* Modification of account information
* Changes to account settings
* Changes to security-related settings
* Other state-changing operations available to the authenticated user

The actual impact depends on the application's implementation and the privileges associated with the affected account.

## 3. Mitigation and Prevention

The primary defense against CSRF is the use of **Anti-CSRF Tokens**.

### Token Generation

The server should generate a unique and unpredictable token associated with the user's authenticated session.

### Token Placement

The token should be included with state-changing requests, commonly as a hidden field within forms.

### Server Verification

When the request reaches the server, the application should verify that the submitted token matches the token associated with the user's session.

Conceptually:

```text
User submits request
        ↓
Server receives request
        ↓
Validate session
        ↓
Validate CSRF token
        ↓
Token valid?
   ┌────┴────┐
  Yes        No
   ↓          ↓
Process     Reject
request     request
```

### Additional Protection

Additional defenses can include:

* Appropriate `SameSite` cookie settings
* Origin or Referer validation where appropriate
* Additional confirmation for particularly sensitive operations
* Avoiding unnecessary state-changing operations through `GET` requests

## Conclusion

The CSRF testing exercise examined the DVWA password-change functionality using Burp Suite. The captured request contained the required password parameters and authenticated session information but **did not contain a dedicated anti-CSRF token**.

The test did not perform a successful forged password change; instead, it demonstrated the absence of token-based protection in the inspected request.

Implementing unpredictable anti-CSRF tokens and validating them on the server provides an effective defense by ensuring that state-changing requests contain information that an external attacker cannot legitimately obtain.
